# DataHub context ablation

This experiment ran the same synthetic incident through three deterministic context scopes. Ground truth is the reviewed replay fixture: two field mappings, eight downstream assets, and eight planned files.

| Mode | Mapping recall | Impacted asset recall | Missing downstream | Owners resolved | File completeness | dbt result |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Incident only | 0/2 (0%) | 0/8 (0%) | 8 | 0 | 0/8 | not run; no patch |
| Recorded schema context | 2/2 (100%) | 0/8 (0%) | 8 | 0 | 0/8 | not run; insufficient lineage |
| Full recorded DataHub context | 2/2 (100%) | 8/8 (100%) | 0 | 3 | 8/8 (100%) | isolated dbt build passed; 9 tests |

Schema descriptions, glossary terms, and ranges are enough to recover the two semantic mappings. They are not enough to identify any downstream consumer or owner. Recorded lineage and entity metadata are what turn the mapping into a bounded multi-file repair. This is the concrete reason DataHub context is central rather than decorative.

The experiment did not measure subjective explanation quality, live DataHub latency, or live model cost. Results are generated by `scripts/evaluate/run_context_ablation.py` and stored in `examples/reports/context-ablation.json`.
